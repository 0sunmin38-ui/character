# 컨텍스트 엔지니어링 요약 (Anthropic)

> 원문: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
> `하네스엔지니어링_AI캐릭터챗봇_01_기초다지기.md`가 이론적 근거로 인용한 문서입니다.
> 아래는 원문 전문이 아니라 캐릭터 챗봇 프롬프트 설계에 쓸 만한 논지를 정리한 요약입니다.

## 핵심 논지

**프롬프트 엔지니어링 → 컨텍스트 엔지니어링.** 좋은 문장을 찾는 문제에서,
추론 시점에 컨텍스트 창에 무엇을 넣을지 매 턴 큐레이션하는 문제로 옮겨갔다는 것.
프롬프트 작성이 일회성 작업이라면 컨텍스트 엔지니어링은 반복적입니다.

**어텐션은 유한한 예산이다.** 컨텍스트가 길어질수록 정보 회수 정확도가 떨어집니다
(needle-in-a-haystack 계열 연구). 트랜스포머 구조상 n개 토큰은 n² 쌍 관계를 만들고,
길이가 늘수록 어텐션이 얇게 퍼집니다. 즉 컨텍스트는 **수확 체감이 있는 유한 자원**이며,
토큰을 추가할 때마다 예산이 깎입니다.

→ 캐릭터 챗봇에 대입하면: 설정을 많이 넣을수록 좋아지지 않고, 어느 지점부터
   캐릭터 일관성이 오히려 무너진다는 근거가 됩니다. 토큰 최적화가 취향이 아니라 구조적 요구.

## 실천 지침

| 지침 | 내용 |
|---|---|
| **고신호 토큰만** | 원하는 결과 확률을 최대화하는 최소 집합을 찾는다. 최소가 곧 짧음은 아님 |
| **올바른 고도(altitude)** | 브리틀한 if-else 하드코딩과 지나치게 막연한 지시 사이의 중간 지대를 노린다 |
| **구조화** | 역할·지침·예시 등 섹션을 나누고 XML 태그나 Markdown 헤더로 구분 |
| **도구는 최소·비중복** | 기능이 겹치거나 비대한 도구 세트는 흔한 실패 원인. 사람이 봐도 어느 걸 쓸지 모호하면 모델도 모른다 |
| **예시는 엄선** | few-shot은 유효하지만 엣지케이스를 잔뜩 욱여넣는 건 역효과 |

## Just-in-time 컨텍스트

모든 데이터를 미리 밀어 넣는 대신, 파일 경로·쿼리·링크 같은 **가벼운 식별자**만 들고 있다가
필요한 시점에 동적으로 불러오는 방식. 사람이 파일 시스템을 쓰는 방식과 비슷합니다.

→ 캐릭터 챗봇의 **로어북**이 정확히 이 패턴입니다. 세계관 전체를 상시 프롬프트에
   박아두는 대신 키워드 트리거로 필요할 때만 주입하는 것이 원문 논지와 일치합니다.

## 긴 호흡(long-horizon) 과제

컨텍스트 창을 넘어가는 긴 작업에서 일관성을 유지하는 세 가지 기법입니다.
장기 대화에서 캐릭터가 무너지는 문제와 그대로 대응됩니다.

| 기법 | 내용 | 챗봇 대입 |
|---|---|---|
| **압축(compaction)** | 한계에 가까워지면 대화를 요약해 핵심만 남기고 새 컨텍스트로 이어감 | 긴 대화의 중간 요약. 무엇을 버리고 무엇을 남길지가 관건 |
| **구조화된 노트** | 컨텍스트 밖의 저장소에 진행 상황을 기록하고 필요할 때 다시 읽어옴 | 관계 변화·사건 로그를 상태창이나 별도 블록으로 관리 |
| **서브에이전트 분리** | 세부 탐색은 별도 에이전트가 맡고 요약만 본 컨텍스트로 반환 | 설정 검색과 대화 생성을 분리하는 구성 |

## 정리

컨텍스트를 무한한 입력이 아니라 **매 턴 큐레이션해야 하는 유한 자원**으로 보는 것이
핵심입니다. 모델이 좋아질수록 지시를 더 많이 적는 게 아니라, 더 적은 고신호 토큰으로
자율성을 주는 방향이 유효하다는 것이 원문의 결론입니다.

→ 캐릭터 챗봇으로 옮기면: 설정을 빠짐없이 적는 것보다, 캐릭터를 규정하는 최소한의
   앵커를 고르고 나머지는 필요할 때 불러오게 만드는 쪽이 낫다는 근거가 됩니다.
